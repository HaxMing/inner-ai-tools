# 知识库调参记录

## 文档用途

本文用于记录 Dify RAG 知识库的分段、Embedding、混合检索、Rerank、Top K、Score 阈值和测试结果。适合回答：

```text
知识库怎么调参？
Top K 应该设置多少？
Score 阈值怎么选？
为什么回答引用不准？
```

## 当前基线配置

```text
知识库名称：内网 Docker/Dify 运维知识库
文档格式：Markdown
Embedding：bge-m3
检索方式：混合检索
Rerank：bge-reranker-v2-m3
Top K：5
Score 阈值：0.35
分段长度：约 600-900 tokens
分段重叠：约 80-120 tokens
```

## 为什么这样配置

### Markdown 文档

Markdown 适合知识库，因为：

```text
1. 标题层级清晰，便于分段。
2. 命令块容易保留格式。
3. FAQ 和操作步骤容易被检索命中。
4. 引用来源更容易定位到具体文档。
```

### 混合检索

混合检索同时利用：

```text
语义相似：适合用户换一种说法提问。
关键词匹配：适合端口、IP、命令、错误文本、模型名。
```

内网运维知识库里有很多精确关键词，例如：

```text
192.168.1.102
19530
invalid schema
docker compose ps
qwen3.6:27b
```

所以混合检索比纯向量检索更合适。

### Rerank

Rerank 用于把混合检索召回的候选片段重新排序，减少无关内容进入 LLM。

## 调参方法

### Top K

Top K 表示最终给 LLM 的片段数量。

建议：

```text
3：回答更聚焦，但可能漏信息。
5：默认推荐，平衡准确率和上下文长度。
8：召回更多，但可能引入噪音和变慢。
```

### Score 阈值

Score 阈值表示低于该相关度的片段会被过滤。

建议：

```text
0.25：宽松，适合文档少或召回不到。
0.35：默认推荐。
0.45：更严格，适合无关引用多。
0.6：很严格，可能导致没有召回。
```

### 分段长度

如果分段太短：

```text
上下文不完整
命令和解释被拆开
LLM 难以理解完整排障流程
```

如果分段太长：

```text
一个 chunk 混入多个主题
Rerank 难以准确排序
引用来源不够精准
```

推荐：

```text
每个 chunk 包含一个完整问题或一个完整操作流程。
标题、原因、命令、验证尽量在同一个 chunk 内。
```

## 测试问题集合

每次调参后，用以下问题测试：

```text
1. Dify Tool 导入 invalid schema 怎么处理？
2. Docker CLI was not found in PATH 是什么原因？
3. Ollama 模型不可用怎么排查？
4. Docker 镜像离线导入后 compose 仍然拉取怎么办？
5. Milvus 19530 端口通但 Dify 用不了怎么办？
6. Rerank 服务不可用会影响什么？
7. Dify 知识库没有召回怎么办？
8. /docs 打开空白是什么原因？
```

## 判断回答质量的标准

好的 RAG 回答应满足：

```text
1. 结论明确。
2. 引用来源与问题相关。
3. 命令可直接复制。
4. 高风险操作有影响说明。
5. 不知道时明确说知识库没有记录。
6. 不编造不存在的服务器、端口、模型或路径。
```

不好的回答表现：

```text
1. 引用不相关文档。
2. 明明工具返回 unhealthy，却回答正常。
3. 给出删除 volume、down -v 等高风险命令但不说明影响。
4. 把 LLM 地址、Embedding 地址、Milvus 地址混淆。
```
